### `cancel_friend_request` FORBIDDEN-vs-NOT_FOUND inconsistency (P3)
Surfaced by a stress-test pass over the Friends client UI (2026-08-12). Every other Friends RPC (remove/block/unblock/respond) returns `NOT_FOUND` when the target relationship no longer exists or isn't visible to the caller, and the client's `runConfirmedAction`/`respondOnce` handlers treat `NOT_FOUND` as a benign, silent dismiss (the row is just gone — nothing to show the user). `cancel_friend_request` instead returns `FORBIDDEN` for that same "not visible to me" case, which the client's status-banner mapping treats as an error state rather than a silent dismiss — so cancelling a request that's already been actioned by the other side (accepted/rejected/removed between the button rendering and the tap landing) surfaces a spurious error banner instead of quietly closing, unlike the equivalent race on every other action in the feature. Fix belongs in a **new** migration (034, since migrations 030–033 are already applied and immutable by this project's convention per `habit-tracker/AGENTS.md`) that changes `cancel_friend_request` to return `NOT_FOUND` for the not-visible case, matching its siblings; the client-side handling already does the right thing once the RPC contract matches. Effort: S (human) → S with CC+gstack (one migration + one RPC status-mapping check, no client logic change needed). Priority: P3 — real but narrow race window, not user-blocking.
